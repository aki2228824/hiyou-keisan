# 2. 運用編（切り替え・バックアップ・セキュリティ）

（2026-11-21 作成。入口は [README.md](README.md)。フォルダ構成は [1_Windowsサーバー編.md](1_Windowsサーバー編.md) と同じ `C:\hiyou\…` を使う。LAN内専用・個人情報ありの前提）

根拠の印: 【実測】= 2026-11-20/21 にこのPC上の複製データ（ダミー患者）と 127.0.0.1:3144 で実際に動かして確認 / 【コード】= ソースで確認 / 【公式】= 公式文書・公式サイトを取得して確認 / 【未検証】= 文書や記憶に基づき、実機では試していない

## 0. 要点

1. アプリは**サーバー機で1プロセスだけ**動かし、DBファイルはサーバーのローカルディスクに置く。「NASの共有フォルダに hiyou.db を置いて各PCで起動する」構成は不可。各プロセスがDB全体をメモリに持ち、保存のたびにファイル全体を上書きするので、後から保存した側が相手の入力を消す【コード server/database.js】。
2. バックアップは「コピー → 検査 → 合格したものだけ世代に入れる」。付属の `backup-hiyou.ps1` を毎晩タスクで実行し、別の機器にも置く。稼働中のDBをエクスプローラーや robocopy で直接コピーしない（2-1）。
3. 通信は HTTPS 化を推奨。条件を満たせば HTTP のまま稼働開始してよい（3章）。HTTPS にするためのアプリ側の対応は、2026-11-21 に適用済み。
4. 入口はサブネット限定のファイアウォール規則1本。ルーターのポート開放、NASの外部公開機能は使わない（4章）。
5. パスワード強度チェック、ログイン失敗時のロック、操作ログは 2026-11-21 に実装した（使い方と月次の確認は 8章）【実測】。アプリに無いのは、二要素認証と、本人がパスワードを変更する画面の2つ【コード】。当面は運用で補い、扱いを施設の責任者と決める（7章）。
6. サーバーは常時稼働が前提。週次送信は月曜 6:00 に起動していないと実行されず、後追いも重複防止も無い【コード server/jobs/scheduler.js、services/weeklyUsage.js】。

## 1. 切替チェックリスト（開発PC → サーバー）

### 1-1 前日まで

1. サーバーのIPを固定する（ルーターのDHCP予約）。
2. サーバーにアプリを配置し、空のDBで起動できることを確認する（[1_Windowsサーバー編.md](1_Windowsサーバー編.md)）。Node.js は 26 系 LTS を入れる（1編 Step 2 と同じ。24 LTS を使うのは 3編の Dockerfile だけ。2026-11-21 の更新で 22.12 以上が必須になった）。開発PCの 25.9.0 は 2026-06-01 でサポート終了【公式 endoflife.date 2026-11-20】。
3. 運用スクリプトはリポジトリの `tools/` に入っている（clone すれば `C:\hiyou\app\tools\` にある。開発PCでは `C:\temp\hiyou-keisan\tools\`）。
4. 新しい SESSION_SECRET をサーバーで作る【実測】。
   ```powershell
   node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
   ```
5. サーバー用 `C:\hiyou\app\.env` を作る（開発PCの .env をコピーして下の3行を足す）。
   ```
   SESSION_SECRET=（手順4の文字列）
   PORT=3000
   DB_PATH=C:/hiyou/data/hiyou.db
   ```
   同じ名前のOS環境変数があると .env より優先される【実測】ので、OS側には設定しない。
6. 切替日時を決めて周知する。月曜 6:00 をまたがない時間帯にし、全員に「保存してログアウト」を依頼する（メンテナンス表示の機能は無い）。

### 1-2 当日

> 開発PCの現在の DB はテストデータだけ（患者 7 名はすべてテスト用の名前。2026-11-21 確認）。本番を**空の DB から始める**（推奨）なら、手順 1〜3 は不要。その場合は手順 5 で `初期管理者を作成しました` と出るのが正常で、直後の手順 6 で必ずパスワードを変える。

1. 開発PCのアプリを止める（止めてからコピーするのが、書き込み途中のファイルを掴まない最も確実な方法）。
2. 開発PCで検査し、表示された件数とハッシュを控える。フォルダが2つある（`c:\temp\hiyou-keisan` と `c:\temp\_hiyou-keisan`、どちらにも data\hiyou.db）ので取り違えない。実際に使っていたのは .env と data\export.log がある `c:\temp\hiyou-keisan` 側。
   ```powershell
   node C:\temp\hiyou-keisan\tools\verify-db.js C:\temp\hiyou-keisan\data\hiyou.db
   Get-FileHash C:\temp\hiyou-keisan\data\hiyou.db -Algorithm SHA256
   ```

3. `hiyou.db` をサーバーの `C:\hiyou\data\` へコピーする（LAN経由。USBメモリを使ったら移行後に消去）。1-1 の確認のあとサーバーのアプリ（サービス）を動かしたままなら、コピーの前に必ず `Stop-Service hiyoukeisan` で止め、前日に作られた空の `C:\hiyou\data\hiyou.db` は別名に変えておく（動いたまま差し替えると、次の保存でメモリ上の空のDBに上書きされる）。サーバーでも検査とハッシュ計算を行い（パスはサーバー用に変える: `node C:\hiyou\app\tools\verify-db.js C:\hiyou\data\hiyou.db` と `Get-FileHash C:\hiyou\data\hiyou.db -Algorithm SHA256`）、ハッシュと件数が開発PCで控えた値と一致することを確認する。**アプリを起動する前に**行う（起動時にファイルを書き直すため【コード database.js】）。
4. サーバーの .env を最終確認: `EXPORT_ENABLED=true`、`DB_PATH`、`SESSION_SECRET`。
5. サーバーでアプリを起動し、ログを見る。
   - 正常: `週次使用量レポート: cron登録 (0 6 * * 1 / Asia/Tokyo)` と `…起動: http://localhost:3000`
   - **`初期管理者を作成しました: admin / admin123` と出たら即停止**。DBを引き継いだのにこう出たら、DBを読めておらず、空のDBが新しく作られている（DB_PATH の場所にファイルが無いと新規作成する。起動ログの `DBファイル:` の行で実際の場所を確認できる。0バイトのファイルは 2026-11-21 の修正で、上書きせずに起動を止めるようになった）。DB_PATH を見直す。
6. admin でログインし、パスワードが初期値（README に記載の admin123）なら直ちに変える（マスタ管理 → ユーザー管理 → 「変更する場合のみ入力」欄）。初期値のままログインすると、画面の上部に注意が出る。新しいパスワードは、基準（13 文字以上、英字と数字の両方を含む、ユーザーIDや password・12345 のような推測されやすい文字列を含まない）を満たさないと登録できない【実測 2026-11-21】。変更後にサーバーで `node C:\hiyou\app\tools\check-default-password.js` を実行すると、初期パスワードのままのユーザーが残っていないか確認できる（「問題なし」と出ればよい）。
7. 個人別アカウントを作る。共有アカウントは作らない。
   - admin（マスタ・ユーザー管理）は1〜2名、入力担当は staff、見るだけの人は viewer。viewer でも全患者の閲覧とPDF出力はできる【コード】。
   - パスワードは 13 文字以上で、英字と数字の両方を含むものでないと登録できない（ユーザーIDや推測されやすい文字列を含むものも不可）【実測 2026-11-21】。ほかのシステムと同じパスワードを使わないことは、アプリでは確かめられないので、運用ルールとして伝える。
   - 同じPCから同じユーザーIDで 5 回続けて間違えると、そのPCからは 15 分間ログインできなくなる（ほかのPCからは入れる）【実測 2026-11-21】。管理者は、マスタ管理 → ユーザー管理 の「ロック解除」ですぐに戻せる（8-2）。
   - パスワードを設定できるのは admin だけ（本人変更の画面は無い【コード routes/users.js】）。本人に admin の画面で直接入力してもらう（ガイドラインは、パスワードを本人しか知り得ない状態に保つことと、担当者が変更したときに本人以外が知り得ない方法で伝えることを求めている【公式 システム運用編14②・⑥(4)】）。
   - パスワードを変えると、その人がログイン中だった画面は次の操作から使えなくなる（2026-11-21 の修正。それ以前は切れなかった）【実測】。「有効」のチェックを外す無効化も、次の操作から即時に効く【コード middleware/auth.js】。
8. 開発PCの二重送信防止: 開発PCの .env を `EXPORT_ENABLED=false` にし、以後そのPCでアプリを起動しない（起動する場合はログに `EXPORT_ENABLED が true でないため無効` と出ることを確認）。旧DBは `hiyou.db.migrated-20261201` のように改名して、誤って旧PCに入力されないようにする。
9. 別のPCから確認する。
   ```powershell
   Test-NetConnection 192.168.1.10 -Port 3000    # TcpTestSucceeded : True
   ```
   ブラウザで staff としてログイン → 患者一覧 → 1件入力して保存 → 請求書PDF（日本語と金額）→ viewer で保存できないこと。来客用Wi-Fiからは**つながらない**ことも確認する。
10. バックアップを1回手動実行し（2-3）、タスクを登録する。
11. 新URLを周知する。8時間でログインが切れること、共用PCでは必ず「ログアウト」を押すことも伝える（Cookie の有効期間が8時間でブラウザを閉じても残る【コード index.js】）。

## 2. バックアップ

### 2-1 このアプリ特有の注意（先に読む）

- 保存のたびにDB全体を書き出す。2026-11-21 の修正で「一時ファイル（`hiyou.db.tmp`）に書いてから差し替える」方式になり、DBファイルが途中までの状態になることは無くなった【実測: 保存中の強制終了30回、保存中の連続コピー144回とも破損なし】。修正前は、保存の最中にコピーすると途中までのファイルが取れた【実測 2026-11-20】。`hiyou.db.tmp` はバックアップの対象にしない。
- 逆に、ほかのプログラム（robocopy、Copy-Item、ウイルス対策、同期ソフト）がDBファイルを掴んでいる間は、アプリの保存が待たされる。約2秒まで再試行し、それでも掴まれたままなら画面に「サーバーでエラーが発生しました」と出る【実測 2026-11-21: 0.7秒の占有は待って成功、4秒の占有は約2.5秒後にエラー】。このとき変更はメモリには入っているがファイルには無い。
  - **保存でエラーが出たら、サーバーを再起動する前にもう一度保存する**（次に成功した保存が全体を書き出す）。再起動するとメモリだけにあった変更が消える。
  - DBのフォルダを OneDrive・NASの同期ソフト・常駐バックアップソフトの対象にしない（同じ理由）。
- 「起動できた」は無事の証拠にならない。中身の一部が壊れたファイルでも起動・ログイン・一覧表示までできた【実測】。判定は必ず verify-db.js の `OK` と件数で行う。

### 2-2 構成

| 置き場 | 内容 | 保持 |
|---|---|---|
| 1本目 `C:\hiyou\backup\daily` / `monthly` | 毎晩の検査済みコピー / 各月最初の1本 | 30世代 / 24世代 |
| 2本目 NAS か USB HDD | 1本目のフォルダの写し | 日次180世代、月次は消さない |
| オフライン（月1回） | `monthly` を暗号化USB（BitLocker To Go）へ。施錠保管 | 施設の決まりに合わせる |

バックアップも個人情報そのもの。置き場の権限は管理者だけにする（4章の icacls）。

backup-hiyou.ps1 の動き【実測 2026-11-21】:
1. アプリの保存を妨げない開き方で読み、コピーする（共有読み取り。コピー中もアプリの保存は成功）。
2. コピー後に本体とコピーのハッシュを比べ、違えば「コピー中に保存された」として捨ててやり直す。
3. verify-db.js で検査（ヘッダのページ数×ページサイズ＝ファイルサイズ、`PRAGMA integrity_check`、各表の件数）。NGならやり直し（最大6回）。
4. 直前の正常世代の半分未満に縮んでいたら `SHRUNK_*.db` として別扱いにし、世代は消さず、終了コード2。人が判断するまで毎晩警告が続く。
5. 2本目へ robocopy（/PURGE なし）。2本目のフォルダが無ければ作らずにエラーにする。`audit` フォルダも一緒に写る。

操作ログ（`C:\hiyou\data\audit\audit-*.jsonl`）は、上の 1 より前に `C:\hiyou\backup\audit` へ複製する（2026-11-21 追加。DB のバックアップに失敗した晩でも写るように、先に行う）【実測: 一時フォルダで 27 項目】。DB のバックアップに失敗した晩も、この複製だけは 2 本目の置き場へ送る（DB のファイルは、検査に通ったものが無いので送らない。backup.log に `operation log: sent to the second device … although the database backup failed` と残る）【実測 2026-11-22: 一時フォルダで 9 項目】。

- 前回より大きくなったファイルだけを写し、何も消さない。アプリが開いたまま追記している今月のファイルも、その時点の長さで写る。
- 操作ログは追記しかされないので、正常なら「前回の複製の続き」になっている。**前回の複製より小さい、前回の複製と書き出しが違う、または大きさが同じなのに中身が違うファイル**は、だれかが消した・書き換えた疑いがある（大きさを変えない書き換え＝ユーザーIDを同じ長さの別のIDに打ち換える、なども見つけられるよう、過去の月のファイルも毎晩中身を比べる。2026-11-22 追加）。その場合は、前回の複製を `audit-YYYY-MM.jsonl.before-日時` という名前で残してから今の内容を写し、WARNING を記録して終了コード 2 にする（警告はその晩の 1 回だけ。残した複製が証拠になる）。
- 1 つのファイルが読めなくても、ほかのファイルは写す（終了コード 1）。
- .env に `AUDIT_LOG_DIR` を書いて保存先を変えている場合は、タスクの引数に `-AuditDir "その場所"` を足す（足さないと、既定の場所に無いので何も写らない。backup.log に `folder not found, nothing copied` と出る）。

約33ミリ秒おきに保存し続ける状態で5回実行し、採用された5世代はすべて「実際に保存されたどれかの状態」とバイト一致、途中状態の採用は0件、やり直し7回【実測】。保存処理の修正後のコードでも確認した（16.6MB の架空データに保存を続けながら5回実行し、5回とも成功、その間のアプリの保存 182 回に失敗なし【実測 2026-11-21】）。

### 2-3 Windows サーバーでの設定

1. 手動で1回実行する（管理者 PowerShell）。
   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File C:\hiyou\app\tools\backup-hiyou.ps1 -DbPath C:\hiyou\data\hiyou.db -AppRoot C:\hiyou\app -LocalDir C:\hiyou\backup
   $LASTEXITCODE                                  # 0
   Get-Content C:\hiyou\backup\backup.log -Tail 2  # [日時] operation log: 1 file(s) copied to C:\hiyou\backup\audit
                                                   # [日時] OK size=… patients=… -> C:\hiyou\backup\daily\hiyou_YYYYMMDD_HHMMSS.db
   ```
2. タスクを登録する【未検証: コマンドはメモリ上でオブジェクト生成まで確認。このPCには登録していない】。
   ```powershell
   $arg = '-NoProfile -ExecutionPolicy Bypass -File "C:\hiyou\app\tools\backup-hiyou.ps1" -DbPath "C:\hiyou\data\hiyou.db" -AppRoot "C:\hiyou\app" -LocalDir "C:\hiyou\backup"'
   $a = New-ScheduledTaskAction -Execute 'powershell.exe' -Argument $arg
   $t = New-ScheduledTaskTrigger -Daily -At '02:30'
   $s = New-ScheduledTaskSettingsSet -StartWhenAvailable -ExecutionTimeLimit (New-TimeSpan -Minutes 30)
   Register-ScheduledTask -TaskName 'hiyou-backup' -Action $a -Trigger $t -Settings $s -User 'SYSTEM' -RunLevel Highest
   ```
3. 2本目がNASのとき: SYSTEM はワークグループ環境のNAS共有に認証できない【未検証・記憶】。サーバーにバックアップ専用のローカルユーザー（例 `hiyou-backup`）を作り（パスワードは無期限にする。期限が切れるとタスクがログオンできず、1本目のバックアップも止まる。作成例: `New-LocalUser -Name 'hiyou-backup' -Password (Read-Host -AsSecureString 'password') -PasswordNeverExpires -AccountNeverExpires`【構文のみ確認】）、NASにも同じ名前・同じパスワードのユーザーを作って共有 `hiyou-backup` だけに書き込み権を与える。そのユーザーに 4章の6 の権限（`C:\hiyou\data` と `C:\hiyou\app` の読み取り、`C:\hiyou\backup` の変更）を付け、次のとおり `-RemoteDir` を足した形でタスクを作り直して登録する（`$arg` を書き換えただけでは、登録済みのタスクには反映されない）。
   ```powershell
   $arg = '-NoProfile -ExecutionPolicy Bypass -File "C:\hiyou\app\tools\backup-hiyou.ps1" -DbPath "C:\hiyou\data\hiyou.db" -AppRoot "C:\hiyou\app" -LocalDir "C:\hiyou\backup" -RemoteDir "\\NAS01\hiyou-backup"'
   $a = New-ScheduledTaskAction -Execute 'powershell.exe' -Argument $arg
   $t = New-ScheduledTaskTrigger -Daily -At '02:30'
   $s = New-ScheduledTaskSettingsSet -StartWhenAvailable -ExecutionTimeLimit (New-TimeSpan -Minutes 30)
   $c = Get-Credential "$env:COMPUTERNAME\hiyou-backup"
   Register-ScheduledTask -TaskName 'hiyou-backup' -Action $a -Trigger $t -Settings $s -User $c.UserName -Password $c.GetNetworkCredential().Password -Force    # -Force = 手順2で登録済みの同名タスクを置き換える
   ```
   2本目がUSB HDDなら、`$arg` に ` -RemoteDir "E:\hiyou-backup"` を足して手順2の `$a =` 以降をもう一度実行する（SYSTEM のまま。登録済みなら `Register-ScheduledTask` の末尾に `-Force` を付ける。`E:\hiyou-backup` フォルダは先に作っておく）。つなぎっぱなしのUSBはランサムウェアから守れないので、2台を月替わりで交換し1台は外して保管する。
4. 登録直後に実行して確かめる。
   ```powershell
   Start-ScheduledTask -TaskName 'hiyou-backup'; Start-Sleep -Seconds 30
   (Get-ScheduledTaskInfo -TaskName 'hiyou-backup').LastTaskResult   # 0
   Get-Content C:\hiyou\backup\backup.log -Tail 2
   ```
   NAS側にも `daily\hiyou_*.db` ができていること。

### 2-4 NAS を使う場合

A. NAS を2本目の置き場にする（アプリは Windows サーバー）
1. 共有フォルダ `hiyou-backup` を作り、権限は 2-3 の専用ユーザーと管理者だけにする。職員の共有とは分ける。
2. その共有にスナップショット（世代保持）を設定する。サーバー側のアカウントが乗っ取られても過去世代を消せなくするため。Synology は Snapshot Replication（Btrfs ボリューム。DSM 7.2 以降の対応機種は消去不能スナップショットも可）、QNAP はスナップショットまたは HBS 3 の世代管理【公式・解説サイトを検索で確認、実機未検証】。

B. NAS の上でアプリを動かす場合（コンテナ）

バックアップは [3_NAS-Docker編.md](3_NAS-Docker編.md) の 9 章（`backup-hiyou.sh`。コピー後にアプリと同じ SQLite で検査し、世代を残す）を使う。保存先の共有は Hyper Backup（Synology）/ HBS 3（QNAP）で USB か別の機器へ世代付きで出し、同じ NAS の中だけに置かない。月次の復元テスト（2-5）は NAS の場合も行う。

### 2-5 復元テスト（月1回、最低でも四半期に1回）

```powershell
$new = Get-ChildItem C:\hiyou\backup\daily\hiyou_*.db | Sort-Object Name -Descending | Select-Object -First 1
New-Item -ItemType Directory -Force C:\hiyou\restore-test | Out-Null
Copy-Item $new.FullName C:\hiyou\restore-test\hiyou.db -Force
node C:\hiyou\app\tools\verify-db.js C:\hiyou\restore-test\hiyou.db C:\hiyou\app     # OK と件数
cd C:\hiyou\app
$env:DB_PATH='C:\hiyou\restore-test\hiyou.db'; $env:PORT='3999'; $env:EXPORT_ENABLED='false'; $env:AUDIT_LOG_DIR='C:\hiyou\restore-test\audit'
node server\index.js
```
上のコマンドは管理者 PowerShell で実行する（`C:\hiyou` は管理者と SYSTEM しか読めないので、通常の PowerShell では「アクセスが拒否されました」になる）。`AUDIT_LOG_DIR` も必ず指定する（確認用の起動での操作を、本番の操作ログに混ぜないため。起動ログの `操作ログ:` の行が `C:\hiyou\restore-test\audit` になっていること）。サーバー上のブラウザで `http://localhost:3999` を開き、ログインして直近の月次集計を本番と見比べる。終わったら Ctrl+C で止め、**その PowerShell ウィンドウを閉じ**（環境変数を残さない）、`C:\hiyou\restore-test` を消す。同じ流れを複製データで実行し、ログインと集計表示まで確認した【実測】。2本目（NAS）の世代でも同じことを年に数回行う。

### 2-6 本番の復元

1. アプリを止める。
2. 現物は消さずに退避する: `Rename-Item C:\hiyou\data\hiyou.db "hiyou.db.broken-$(Get-Date -Format yyyyMMdd_HHmm)"`
3. 戻す世代を選んでコピーする: `Copy-Item C:\hiyou\backup\daily\hiyou_YYYYMMDD_HHMMSS.db C:\hiyou\data\hiyou.db`
4. `node C:\hiyou\app\tools\verify-db.js C:\hiyou\data\hiyou.db C:\hiyou\app` が OK で、件数が妥当なこと。
5. 起動し、ログに `初期管理者を作成しました` が**出ていない**ことを確認する。
6. その世代の時刻以降の入力は無いので、再入力が必要な範囲を職員に伝える。
7. マルウェアが疑われるときは自分で戻さず、まず施設の責任者へ（ガイドラインも、不用意な復旧が被害を広げる危険を指摘している【公式 システム運用編11・18.1】）。
8. 操作ログ（`C:\hiyou\data\audit`）は DB とは別のファイルなので、DB を戻しても巻き戻らない（そのまま残し、消さない）。DB の差し替えのように、サーバー上で直接行った作業はアプリの操作ログには残らないので、日時・担当者・理由を業務日誌に書く。
9. **サーバーを作り直した場合**（`C:\hiyou\data\audit` が無い場合）は、アプリを起動する前に、バックアップの `audit` フォルダにある `audit-*.jsonl`（名前に `.before-` が付いたものは除く）を `C:\hiyou\data\audit` へコピーする。コピーせずに起動すると、それまでの操作ログが画面に出なくなり、翌晩の backup.log に操作ログの WARNING（`is smaller`）が 1 回出る。

### 2-7 ログの読み方

| backup.log の行 / 現象 | 意味 | すること |
|---|---|---|
| `try N failed: the app saved while the file was being copied` の後に OK | コピー中に保存があり、やり直して成功 | 何もしない |
| `ERROR no verified backup after 6 tries`、`BAD_hiyou_*.db` | 6回とも不合格 | verify-db.js の NG 理由を見る。本体が壊れていれば 2-6 |
| `WARNING … less than half …`、`SHRUNK_hiyou_*.db`、終了コード2 | DBが急に小さくなった（空のDBで起動した疑い） | 件数を確認。誤りなら 2-6。意図した縮小なら `-AllowShrink` を付けて1回だけ手動実行 |
| `ERROR second device folder not found` | NAS停止か、パス間違い | NASと共有名を確認（フォルダは自動作成しない） |
| `ERROR not found: …` | DB・node.exe・verify-db.js・sql.js のどれかが無い | パスの引数を直す |
| `operation log: N file(s) copied to …` | 操作ログを複製した（N は、前回より大きくなったファイルの数。0 のこともある） | 何もしない |
| `operation log: sent to the second device … although the database backup failed` | DB のバックアップに失敗した晩に、操作ログの複製だけを 2 本目の置き場へ送った | DB の失敗の原因（同じ晩の `ERROR` の行）を調べる |
| `WARNING operation log audit-… is smaller …` / `… no longer starts with the content of its backup copy …` / `… has the same size as its backup copy but different content …`、終了コード2 | 操作ログのファイルが、前回の複製より小さい、または書き換えられている（削除・切り詰め・書き換えの疑い） | だれがサーバー上でファイルを操作したか確認する。前回の複製は `audit-…jsonl.before-日時` として残っている。警告はその晩だけ（翌晩は出ない） |
| `ERROR operation log copy failed for audit-…`、終了コード1 | そのファイルを複製できなかった（ほかのファイルと DB のバックアップは行われる） | メッセージの理由（ほかのプログラムが開いている、権限、空き容量）を確認する。翌晩に複製される |
| `operation log: folder not found, nothing copied: …` | 操作ログのフォルダが、その場所に無い | 操作ログを入れる前の版なら正常。.env で `AUDIT_LOG_DIR` を変えているなら、タスクに `-AuditDir` を足す |
| `ERROR operation log folder not found: …（given with -AuditDir）`、終了コード1 | `-AuditDir` で指定したフォルダが無い | 引数の書き間違いを直す |
| `operation log: … (N month file(s) exist only in the backup …)` | バックアップにある月のファイルが、元のフォルダに無い | 古い月を整理（移動）したのなら正常。心当たりが無ければ、だれが消したか確認する |

根本対策は 2026-11-21 に実施済み: 保存を「一時ファイルに書いてから差し替える」方式にしたので、途中状態のDBファイルは存在しなくなった。backup-hiyou.ps1 の検査とやり直しは保険として残している。

## 3. HTTPS

### 3-1 結論

**HTTPS にする**（同じサーバー上のリバースプロキシで終端し、内部用の証明書を使う）。ただし次の2つを両方満たすなら、HTTP のまま稼働を始めて後から切り替えてよい。

- 使うPCが全部有線で、来客・業者の機器が同じセグメントにつながらない
- 4章のファイアウォール規則でサブネット限定にしてある

Wi-Fi で使うPCが1台でもあるなら、最初から HTTPS にする。

理由:
1. 今は HTTP だけで、ログインのパスワード、ログイン状態の Cookie、患者氏名・受給者証番号・請求書PDF が毎回平文で流れる【コード】。同じLANの感染PCや不正機器から読める。
2. 厚労省ガイドラインは、セッション乗っ取りの防止、回線または情報の暗号化、改ざん・中間者攻撃の防止を求め、境界防御だけに頼らない考え方を示している【公式 システム運用編13・13.2・13.3】。施設内LANのHTTPを名指しで禁じる記述は見当たらなかったが、HTTPS にしておけば説明が簡単になる（私の読み取りであり法的判断ではない）。
3. 3〜10台なら手間が小さい。証明書の登録は1台数分で、Caddy は証明書を自動更新する【公式】。
4. ブラウザに強制されるわけではない。Chrome は 2026年10月（154）から公開サイトの HTTP に警告を出すが、192.168.x.x などのプライベートアドレスは対象外【公式ブログ等を検索で確認 2026-11-21】。

注意: 証明書を入れていないPCが1台でもあると、その人は警告を「無視して進む」ことを覚えてしまう。全PCに入れてからURLを切り替える。

### 3-2 手順A: Windows サーバー + Caddy【未検証: このPCでは caddy.exe の実行がブロックされ試せなかった。設定は公式文書に基づく】

1. https://caddyserver.com/download か GitHub の Releases から Windows amd64 版を取り（2026-11-21 時点の最新は v2.11.9【公式】）、`C:\caddy\caddy.exe` に置く。
2. `C:\caddy\Caddyfile` を付属の内容で作る（IP は実際のものに）。
3. 80 と 443 を他が使っていないこと: `Get-NetTCPConnection -LocalPort 80,443 -State Listen`（空いていれば赤字で「一致する MSFT_NetTCPConnection オブジェクトが…見つかりません」というエラーが出る。これが空きの印。行が表示されたらそのポートは使用中）。
4. まずコンソールで試す: `cd C:\caddy; .\caddy.exe run --config C:\caddy\Caddyfile`。エラーが無ければ、サーバー上で `curl.exe -k -I https://192.168.1.10/` が `200` を返す。
5. ファイアウォール: 443（と、HTTP からの自動転送用に 80）をサブネット限定で許可し、3000 の許可規則は消す（[1_Windowsサーバー編.md](1_Windowsサーバー編.md) Step 8 の規則の `-LocalPort` を変える）。3000 を閉じるのは、手順6で全PCに証明書を入れ、HTTPS で開けることを確認してからにする（先に閉じると、証明書を入れていないPCは警告が出て使えない）。
6. ルート証明書 `C:\caddy\data\pki\authorities\local\root.crt` を各PCへコピーし、管理者 PowerShell で登録する（Chrome / Edge は Windows の証明書ストアを使う）。
   ```powershell
   Import-Certificate -FilePath .\root.crt -CertStoreLocation Cert:\LocalMachine\Root
   ```
   `https://192.168.1.10/` を開いて警告が出ないこと。
7. 手順4でコンソールに起動した Caddy を Ctrl+C で止めてから、サービスにする（管理者）。
   ```powershell
   sc.exe create caddy start= auto binPath= "C:\caddy\caddy.exe run --config C:\caddy\Caddyfile"
   sc.exe start caddy
   ```
   `sc.exe create … caddy.exe run` は公式手順【公式】、`--config` の指定は私の追加【未検証】。設定変更後はサービスの再起動で反映する。
8. サーバーの .env に `TRUST_PROXY=loopback` と `HOST=127.0.0.1` を足して `Restart-Service hiyoukeisan`（アプリ側の対応は 2026-11-21 に適用済み。3-4）。起動ログに `待ち受けは 127.0.0.1 のみ` と `TRUST_PROXY=loopback` が出ること。HTTPS でログインし直し、マスタ管理 → 操作ログ の「接続元」が、サーバーの 127.0.0.1 ではなく自分のPCのアドレスになっていることを確かめる。
9. `C:\caddy\data` には内部CAの秘密鍵がある。フォルダの権限を管理者と SYSTEM だけにする（4章の icacls）。漏れると職員PCが信用する証明書を誰でも作れる。
10. 監視スクリプトの `-Url` を `https://192.168.1.10/` に変える（監視するPCにも証明書を入れる）。

補足【公式 Caddy 文書】: ルート証明書の有効期間は約10年（3600日）、中間は7日、サーバー証明書は12時間で、中間証明書とサーバー証明書は Caddy が自動更新する。ルート証明書は自動更新されない（期限が近づくとログに警告が出るだけ）ので、約10年後の期限前に作り直して各PCへ入れ直す。IPアドレスが変わったら Caddyfile を直す。

### 3-3 手順B: NAS 内蔵のリバースプロキシ（アプリをNASで動かす場合）【未検証】

1. Synology DSM 7: コントロールパネル → ログイン ポータル → 詳細 → リバース プロキシ → 作成。ソース = HTTPS / ポート（例 8443）、宛先 = HTTP / localhost / 3000。QNAP QTS 5: コントロールパネル → ネットワークとファイルサービス → ネットワークアクセス → リバースプロキシ【公式チュートリアルと解説サイトを検索で確認】。
2. 証明書: NAS 既定の自己署名証明書は名前が合わず警告になる。NASのIPを含む証明書を自前のCAで作って取り込む。Git for Windows の openssl で作成と検証まで確認した手順【実測】:
   ```bash
   openssl req -x509 -newkey rsa:3072 -sha256 -days 3650 -nodes -keyout hiyou-root.key -out hiyou-root.crt -subj "/CN=Hiyou Internal Root CA" -addext "basicConstraints=critical,CA:TRUE" -addext "keyUsage=critical,keyCertSign,cRLSign"
   openssl req -newkey rsa:2048 -nodes -keyout hiyou-server.key -out hiyou-server.csr -subj "/CN=192.168.1.20"
   openssl x509 -req -in hiyou-server.csr -CA hiyou-root.crt -CAkey hiyou-root.key -CAcreateserial -out hiyou-server.crt -days 825 -sha256 -extfile server.ext
   openssl verify -CAfile hiyou-root.crt hiyou-server.crt      # hiyou-server.crt: OK
   ```
   Git Bash では先頭に `MSYS_NO_PATHCONV=1 ` を付ける（`/CN=…` がパスに変換されるのを防ぐ）。`server.ext` は付属の内容だが、中の `IP:192.168.1.20` と、上のコマンドの `-subj "/CN=192.168.1.20"` は NAS の実際の IP に書き換える（3編の例では 192.168.1.50。`DNS:nas01` も実際の名前に）。NAS に hiyou-server.crt / .key（中間証明書の欄に hiyou-root.crt）を取り込み、リバースプロキシに割り当てる。各PCには hiyou-root.crt を 3-2 の手順6と同じコマンドで登録する。hiyou-root.key はオフラインで保管する。有効期間は825日なので更新日を予定表に入れる。
3. アプリの .env は `TRUST_PROXY=1`（コンテナから見た接続元がNAS本体になるため loopback では効かない）。

### 3-4 アプリ側の対応（**2026-11-21 に適用済み**。server/index.js）

コードの変更は済んでいるので、HTTPS にするときに行うのは .env の2行だけ（Caddyfile と server.ext は `配置手順/付属ファイル/https/` にある）。

| .env | 効果 |
|---|---|
| `TRUST_PROXY=loopback`（Caddy 同居）/ `1`（NAS） | プロキシが伝える「HTTPSで届いた」「本当の接続元」という情報を信用する。ログイン用 Cookie に Secure 属性が付き、操作ログの接続元が利用者のPCのアドレスになる |
| `HOST=127.0.0.1`（Caddy 同居のときだけ） | 3000 番へはサーバー自身からしかつながらなくなる |

本物の TLS を終端するプロキシ越しに確認した結果【実測 2026-11-21。Caddy は実行できないため、Caddy の既定のヘッダーの扱い（公式文書の reverse_proxy「Defaults」: X-Forwarded-For / Proto / Host を付け直し、利用者が送ってきた値は無視する）に合わせた確認用プロキシと、テスト用の認証局・証明書を使用。証明書の検証は有効のまま。24 項目】:

- HTTPS でログインでき、Cookie に `Secure; HttpOnly; SameSite=Lax` が付く。API も請求書 PDF も HTTPS 経由で動く。実際のブラウザー（ヘッドレス Chrome）での画面操作 29 項目も HTTPS 経由で合格。
- `HOST=127.0.0.1` のとき、LAN のアドレスからアプリのポートへは接続できない（プロキシのポートだけが開く）。サーバー自身からの HTTP 直接接続は従来どおり使える。
- 操作ログの接続元は、プロキシの 127.0.0.1 ではなく利用者のPCのアドレスになる。利用者が X-Forwarded-For ヘッダーを偽って送っても、記録されるのは本当の接続元（プロキシが付け直すため）。サーバー機の上から 3000 番へ直接つないだ場合だけは偽れる（サーバー機にログオンできる人に限られる）。
- `TRUST_PROXY` を書き忘れても、ログインはできる（Cookie の Secure 属性は「HTTPS で届いた要求にだけ付ける」設定のため、付かないだけ）。ただし操作ログの接続元がすべて 127.0.0.1 になるので、HTTPS にしたら必ず書く。
- .env に何も足さなければ、動きは HTTP のままで従来と同じ。

注意:

- `TRUST_PROXY=true` は使えない（どこから来た要求でもヘッダーの内容を信用してしまうため、起動時にエラーで止まる）。書き間違い（`loopbak` など）も、理由を表示して起動を止める【実測】。
- `TRUST_PROXY=1` は、アプリへ届く経路がプロキシだけの構成（NAS のコンテナ。3-3）でだけ使う。利用者が 3000 番へ直接つなげる構成で書くと、ヘッダーを付けて送るだけで接続元や HTTPS の情報を偽れる。プロキシを使わない構成では `TRUST_PROXY` を書かない。
- Caddy を使う場合、3000 の許可規則は必ず消す（3-2 の 5）。
- プロキシの信用判定に使う proxy-addr に出ていた critical の指摘は、2026-11-21 の依存ライブラリの更新で解消した（5章の 8）。

## 4. アクセス制限

1. Windows ファイアウォール: [1_Windowsサーバー編.md](1_Windowsサーバー編.md) の Step 8 のとおり、TCP 3000 の受信を同一サブネットからだけ許可する規則を1本作り、node.exe 向けに自動で作られた規則は消す。
   - node を初めて起動したときのダイアログで「許可」を押すと、全ポート・全アドレス許可の規則ができる（開発PCに実物があった: Inbound Allow / Public / ポート Any / 相手 Any【実測】）。「キャンセル」を押した場合は同じ名前のブロック規則ができ、ブロックは許可より優先される【公式 Microsoft Learn】。
   - 規則を Private / Domain だけにしておくと、ネットワークが「パブリック」と判定された日はつながらない（安全側に倒れる）。
   - PCのIPが固定なら `-RemoteAddress 192.168.1.21,192.168.1.22` のように列挙するとさらに絞れる。
2. ルーター: ポート開放（ポートフォワード）をしない、UPnP を切る、DMZ にしない。NAS の外部アクセス機能（QuickConnect、myQNAPcloud、DDNS）を使わない。サーバーに遠隔操作ソフトやトンネル系サービスを入れない。自宅からの保守は、施設のルールが決まるまで行わない。
3. Wi-Fi: 来客用は別SSIDにし、ルーターのゲスト分離を有効にする。このアプリを使うPCは有線を基本にする。ガイドラインは無線LANについて利用者の制限と WPA2-EAP / WPA3 等での暗号化を求め、共有パスフレーズ方式（WPA2-PSK など）は避けるよう書いている【公式 システム運用編13⑬・13.4】。
4. 外向き通信: 週次送信のため、サーバーから送信先（.env の DIFY_API_URL）への HTTPS だけは必要。送る中身は品目別の集計値で個人情報は含まない。
5. サーバー機: 施錠できる場所に置く。ディスクは BitLocker。画面ロック。メールやWeb閲覧に使わない。Windows Update と Defender を有効のままにする。時刻同期を確認する（`w32tm /query /status`）。

## 8. パスワード・ロック・操作ログの運用（2026-11-21 追加）

### 8-1 パスワードの基準

登録・変更のときに、アプリが次の点を確かめる【実測】。満たさないものは登録できず、足りない点が画面に表示される。

- 13 文字以上（72 文字まで）。半角の英字と数字を両方含む（大文字・小文字は問わない。記号は使えるが必須ではない）
- ユーザーID、推測されやすい文字列、同じ文字の 4 回以上の連続、順番に並んだ文字（12345、abcde）、同じ並びの繰り返し（abc123abc123）を含まない。推測されやすい文字列とは、password・admin・welcome などのよくある語、**hiyou・keisan・byouin・hospital・ryouyou・kaigo のような施設や業務に関係する語**、qwerty・asdfg・1q2w3e などのキーボードの並び（pa55word のように数字や記号で置き換えたものも含む）。断られたときは、当たった語が画面に表示される
- 6 種類以上の文字を使う
- 変更のときは、現在のパスワードと同じものは不可（8-2 の非常用のツールだけは、忘れたときに使うものなので、この確認をしない）

根拠は、ガイドラインの「二要素認証を採用していない場合には 13 桁以上」「英数字の混在（大文字小文字は問わない）」「類推されやすいパスワードを使用させないよう、設定可能なパスワードに制限を設ける」【公式 システム運用編 14⑥(1)・14.1 の解説】。同じ解説により、定期的な変更は不要。

- 文字数は .env の `PASSWORD_MIN_LENGTH` で変えられる（既定 13。8 未満にはできない）。8 に下げてよいのは、二要素認証を導入した場合だけ。
- 基準ができる前に決めたパスワードや、初期の admin123 は、そのままでもログインできるが、ログインのたびに画面の上部へ注意が出る。操作ログにも「パスワードが基準を満たしていない」と残るので、月次の確認で拾える。
- **パスワードを変更すると、そのユーザーがログイン中だった画面は、次の操作から使えなくなる**（ログインし直しになる）【実測】。パスワードが漏れた疑いがあるときは、変更するだけで古いログイン状態も切れる。管理者が自分自身のパスワードを変えた場合は、操作中の画面をそのまま使える。
- 初期パスワードのままのユーザーが残っていないかは、従来どおり `node C:\hiyou\app\tools\check-default-password.js` でも確認できる。
- 「ほかのシステムと同じパスワードを使わない」は、アプリでは確かめられない。発行のときに口頭と書面で伝える。

### 8-2 ログイン失敗時のロック

ガイドラインの「一定回数、認証に失敗した場合には、以降一定時間ログイン試行が不能となる仕組み」【公式 システム運用編 14⑥(6)】に当たる。数え方は2段階【実測】。

| 数える単位 | 回数 | ロックされる範囲 |
|---|---|---|
| 同じPC（接続元）から、同じユーザーIDで | 5 回続けて失敗 | **そのPCから**そのユーザーIDへのログインが 15 分間できない（正しいパスワードでも不可） |
| 同じユーザーIDで、すべてのPCの合計 | 15 分間に 20 回失敗 | **どのPCからも**そのユーザーIDでログインできない（15 分間） |

- 2段階にしてあるのは、1台のPCからわざと間違え続けるだけで本人や管理者まで締め出される、ということを防ぐため。1台がロックされても、本人はほかのPCからログインできる。PCを変えながら試し続けた場合は、合計 20 回で全体がロックされる。
- 15 分たてば自動で戻る。すぐに戻すには、管理者が マスタ管理 → ユーザー管理 を開き、「ロック中」（どのPCからも入れない）または「一部のPCでロック中」（そのPC以外からは入れる）と出ているユーザーの「ロック解除」を押す。パスワードを設定し直したときも解除される。解除する前に、本人が間違えたのかを確かめる（心当たりが無ければ、操作ログでその時刻の「接続元」を見る）。
- ロックされるのはログインだけ。すでにログインしている画面は、そのまま使える。
- 回数と時間は .env の `LOGIN_MAX_FAILURES`（既定 5、3〜20。全体の回数はその 4 倍）と `LOGIN_LOCK_MINUTES`（既定 15、1〜1440）で変えられる。
- 実在しないユーザーIDでも同じようにロックの表示になる（ユーザーIDが実在するかどうかを、外から調べられないようにするため）。
- これとは別に、ログインの試行そのものに上限がある（同じ接続元から 1 分間に 20 回、全体で 1 分間に 120 回。超えると「ログインの試行が多すぎます」と出る）。でたらめなログインを連打されても、ほかの人の操作が重くならないようにするため【実測: 対策前は 30 本の同時連打で、ほかの操作の応答が約 4 秒になった】。
- HTTPS のプロキシ（3章）を使っていて `TRUST_PROXY` を書いていない場合、アプリからは全員が同じ接続元（127.0.0.1）に見えるので、接続元ごとの区別は働かない（1台の失敗で、そのユーザーIDが全員ロックされる）。HTTPS にしたら必ず `TRUST_PROXY` を書く。

**管理者がログインできなくなったとき**

1. ロックなら、15 分待つか、ほかのPC（またはサーバー機のブラウザー）からログインする。管理者を 2 名にしておくと、互いに解除できる。
2. 急ぐ場合は `Restart-Service hiyoukeisan`（失敗の回数とロックはサーバーのメモリ上にあるので、再起動で消える。全員ログアウトになる点に注意）。
3. **パスワードを忘れた場合**は、サーバー機で非常用のツールを使う（**新しく開いた**管理者 PowerShell で。復元テスト（2-5）などで `$env:DB_PATH` や `$env:PORT` を設定したウィンドウは使わない）【実測 2026-11-22: 一時的に複製したDBと疑似的な端末で 24 項目。回帰テストと自己テストにも計 5 項目】。
   ```powershell
   Stop-Service hiyoukeisan                              # 全員ログアウトになる
   node C:\hiyou\app\tools\reset-password.js --list      # 登録されているユーザーIDを確認
   node C:\hiyou\app\tools\reset-password.js admin       # 新しいパスワードを2回入力
   Start-Service hiyoukeisan
   ```
   - 最初に表示される「DBファイル:」の行が `C:\hiyou\data\hiyou.db` であることを確かめる。DB が見つからないときは「DBファイルが見つかりません」と出て、何も変更せずに終わる（DB を新しく作ることはしない）。
   - 「新しいパスワード: 」「もう一度: 」と表示されたら入力する。**打った文字は画面に表示されない**（カーソルも動かない）。打ち終えたら Enter。やめるときは Ctrl+C（何も変更されない）。
   - アプリが動いている間は実行できない。「アプリが動いています」または「動いているかどうかを確かめられませんでした」と出たら、`Get-Service hiyoukeisan` の Status が Stopped になっているかを確かめてから、もう一度実行する。入力を待っている間にアプリが起動した・DB が書き換えられた場合も、何も変更せずに終わる。
   - `--list` で「無効」と表示されるユーザーを指定すると、**有効に戻る**（入力の前に注意が表示される）。退職した人のIDなど、無効のままにしておくユーザーは指定しない。
   - 新しいパスワードも 8-1 の基準を満たす必要がある（「現在と同じものは不可」の確認だけは行わない）。実行したことは操作ログに「パスワードの再設定（サーバー上のツール）」として、Windows のユーザー名つきで残る（操作ログの画面では、種類を「サーバーの出来事」にすると出る）。このツールを使えるのはサーバー機の管理者だけなので、サーバー機の管理者権限そのものを厳重に管理する（4章の 5・6）。

### 8-3 操作ログ

**何が記録されるか**【実測・コード server/middleware/audit.js、routes/auth.js】

- ログインの成功・失敗・ロック中の拒否、ログアウト
- 患者一覧・実績・月次集計・食事単価の表示、請求書 PDF の出力
- 実績・単価・患者・物品・病棟・ユーザーの登録・変更・削除（権限が無くて断られたもの、入力の誤りで断られたものも含む）、ロックの解除、週次レポートの手動実行
- 操作ログそのものの表示、サーバーの起動、サーバー上のツールでのパスワードの再設定

1 件ごとに、日時（サーバーの時刻）、ユーザーID とロール、接続元の IP アドレス、操作の種類、対象の患者ID、結果、変更の内容が残る。病棟・物品・単価の一覧のような参照用データの表示は記録しない。ガイドラインの「少なくとも利用者のログイン時刻、アクセス時間及びログイン中に操作した医療情報が特定できるように記録する」【公式 システム運用編 17①】に当たる。

記録のしかたで知っておくこと:

- **パスワードは記録されない**（`***` に置き換わる）。ログインに失敗したときに入力されたユーザーIDは、登録されているIDのときだけ残す。登録されていない文字列は「登録されていないユーザーID（○文字）」とだけ残す（ユーザーIDの欄にまちがえてパスワードを打つことがあるため）。
- ID を `1.0` や `0001` のような変則的な書き方で送っても、どの患者・どのユーザーかは同じように残る（送られてきた値も併せて残る）【実測】。
- `/api/pdf//…` のように `/` を重ねたURLや、`%00` を含むURLは、処理せずに断る（404・400）。断ったことは、操作の種類と患者ID つきで残る【実測 2026-11-22: 対策前は、`/` を 1 つ余分に打つだけで、記録が 1 行も残らないまま実績や請求書 PDF を取得できた】。患者の情報を返す要求は、URL の書き方にかかわらず必ず記録の対象になる（記録しないのは、病棟・物品・単価の一覧とパスワードの基準の表示だけ）。
- 未ログインの要求（ログインしていない人が送ってきたもの）は、内容を記録せず、1 件ずつ記録するのは 1 分間に 120 件まで。超えた分は「多すぎた要求（件数だけを記録）」の 1 行にまとまる（だれでも送れる要求で、ログを際限なく増やせないようにするため【実測: 対策前は 1 台から毎秒 約 11MB 増やせた】）。ただし、実在するユーザーへのログイン失敗と、ロックがかかった瞬間は、この上限に関係なく必ず残る。
- ログイン済みのユーザーが、記録の対象になる操作を 1 分間に 6,000 件を超えて送った場合（人が画面を操作して届く数ではない。全病棟の月次集計でも、1 回の表示で「患者数＋1」件）、**超えた分は処理せずに断る**（画面には「操作が多すぎます。1分ほど待ってから、もう一度お試しください」と出る）。断った件数は「多すぎた要求」の 1 行に、操作の種類ごとに残る。処理した操作は必ず 1 件ずつ残るので、要求を連打して「どの患者を見たか」を記録から消すことはできない【実測 2026-11-22: 対策前は、上限（当時 1,200 件）を超えた分を 1 行にまとめていたため、無関係な患者ID を 500 件送ってから開いた患者の実績・月次集計・請求書 PDF が、記録に残らなかった】。上限は .env の `AUDIT_USER_PER_MINUTE` で変えられる（既定 6000。600〜60000。通常は変更しない）。
- 保存先に書き込めない状態が起きた場合は、書けるようになった時点で「記録の欠落（件数）」が残る。

**記録されないもの**: サーバー機の上で直接行った作業（DB ファイルの差し替え・復元、.env の変更、サービスの再起動など）。これらは業務日誌に残す。

**保存先**: `C:\hiyou\data\audit\audit-YYYY-MM.jsonl`（DB と同じフォルダの `audit`。1 か月 1 ファイル、1 行が 1 件）。DB とは別のファイルで、追記だけを行う。アプリには書き換え・削除の機能が無い。自動では消えない。

**月次の確認**（管理者。マスタ管理 → 操作ログ。期間の初期値はサーバーの今日）

1. 期間を前月の 1 日〜末日にし、種類を「断られた操作・エラー」にして表示する。権限の無い操作が繰り返されていないか、見覚えのない接続元が無いか、「多すぎた要求」「記録の欠落」が出ていないかを見る。
2. 種類を「ログイン・ログアウト」にして表示する。ログイン失敗の連続、深夜・休日のログイン、退職・異動した人のユーザーIDでのログインが無いかを見る。
3. 種類を「サーバーの出来事」にして表示する。「サーバーの起動」「パスワードの再設定（サーバー上のツール）」「サーバーの警告」に、心当たりの無いものが無いかを見る（起動し直すとログイン失敗の回数とロックが消えるので、心当たりの無い起動には注意する）。
4. 特定の患者について「だれが見たか」を調べるときは、キーワードに患者の氏名（一部でよい）を入れる。**削除した患者や、氏名を変える前の記録は、氏名では見つからない**ので、「患者ID」の欄に患者ID を入れて探す（患者ID は、その患者の「患者の削除」「患者の変更」の記録の「対象」に出ている）。特定の職員については、ユーザーID欄に入れて絞り込む。
5. 「CSV保存」で保存し、確認した日と担当者を業務日誌に書く（CSV は Excel で開ける。1 回に保存できるのは新しい順に 5,000 件までなので、多い月は期間を分ける）。

ガイドラインも、全部のログを目で見るのではなく、絞り込んだものを定期的に確認することを想定している【公式 システム運用編 17.1】。

**保護とバックアップ**

- 見られるのは管理者ロールだけ。ファイルそのものは `C:\hiyou\data` の中にあり、1編 Step 3 の権限（管理者と SYSTEM だけ。4章の 6）で守られる。操作ログにも患者ID や変更内容が入っているので、DB と同じ扱いにする。
- 毎晩のバックアップ（2章）が `C:\hiyou\backup\audit` と 2 本目の置き場へ複製する（DB のバックアップに失敗した晩も、操作ログは 2 本目まで届く）。サーバー上のファイルを消されたり書き換えられたり（大きさを変えない書き換えを含む）しても、その前の複製は別名（`…jsonl.before-日時`）で残り、backup.log に WARNING が出る（2-7）。
- サーバーの時刻がずれるとログの時刻もずれる。時刻同期（4章の 5）を確認しておく。
- HTTPS（3章）にしたら、.env の `TRUST_PROXY` を必ず書く。書かないと、接続元がすべて 127.0.0.1 と記録される。

**容量と整理**

- 1 件は 200〜800 バイト【実測】。患者 120 人の実績を毎日入力する使い方で、1 か月 3〜10MB、1 年で 50〜120MB の見込み（1 件あたりの実測からの試算）。
- 画面での表示は、1 か月分が 10 万件（34MB）のとき 0.3 秒、100 万件（340MB）のときでも約 3 秒【実測。ほかの人の操作は止まらない】。
- 保存期間は施設の規程に合わせる（ガイドラインのシステム運用編・企画管理編・Q&A を検索した範囲では、ログの保存年数の定めは見当たらなかった）。古い月のファイルを整理するときは、消す前に別の媒体へ写す。前月までのファイルは、アプリが動いていても移動できる（アプリが開いているのは今月のファイルだけ）。移動した月の分は、画面では見られなくなる。

**うまくいかないとき**

| 症状 | 原因と対処 |
|---|---|
| 操作ログの画面に「書き込めなかった記録が N 件あります」、一覧に「記録の欠落」 | 保存先に書けない状態が起きた（ディスクの空き、フォルダの権限）。業務は止めずに動き続けるが、その間の記録は残っていない。原因を直すと、次の操作から記録が再開する |
| 一覧に「多すぎた要求（件数だけを記録）」 | 未ログインの要求が短時間に集中した（1 件ずつの記録を省略した件数）、または同じユーザーの操作が 1 分間の上限を超えた（処理せずに断った件数。内容の欄に、操作の種類ごとの件数が出る）。接続元（未ログインの場合は、同じ時刻の前後の行）を見て、そのPCを調べる |
| 利用者の画面に「操作が多すぎます。1分ほど待ってから…」 | 同じユーザーの操作が、1 分間の上限（既定 6,000 件）を超えた。人の操作では届かない数なので、そのユーザーIDで何か（プログラムなど）が動いていないかを調べる。1 分たてば、また使える |
| 起動しない。ログに `操作ログの初期化エラー` | 保存先フォルダを作れない・書けない（1編 §8）。DB は開かれていない |
| 接続元がすべて 127.0.0.1 | HTTPS のプロキシの後ろで `TRUST_PROXY` を書いていない（3-4） |
| 今日の記録が出ない | 期間の欄を確かめる（初期値はサーバーの今日。サーバーの時計・タイムゾーンが違っていると、日付がずれる。4章の 5） |
| 画面が開けないときにログを見たい | 管理者 PowerShell で直接読める（例は下） |

```powershell
# 例: 今月の「断られた操作・エラー」と「ログイン関係」を一覧にする
Get-Content C:\hiyou\data\audit\audit-2026-11.jsonl -Encoding UTF8 | ForEach-Object { $_ | ConvertFrom-Json } |
  Where-Object { $_.action -like 'login.*' -or $_.status -ge 400 } | Format-Table t, user, ip, action, status -AutoSize
```
