# 配置手順（社内サーバーに置いて、複数のPCから使う）

このアプリを開発PCではなく常時稼働のサーバー機に置き、社内ネットワーク（LAN）内の複数のPCのブラウザーから使えるようにするための手順書です。2026-11-21 作成。

## 結論

- **常時稼働できる Windows PC を1台用意し、Windows サービスとして動かす**のが最も確実です。手順は [1_Windowsサーバー編.md](1_Windowsサーバー編.md)。
- NAS は、Synology / QNAP の Intel・AMD 機（メモリ 4GB 以上）ならコンテナで動かせます（[3_NAS-Docker編.md](3_NAS-Docker編.md)。**Docker 上では未テスト**）。Buffalo や I-O DATA の NAS では動かせないので、バックアップ先として使います。
- どの方式でも、**サーバープロセスは1つだけ**です。NAS の共有フォルダに DB やプログラムを置いて各PCで起動する使い方はできません（互いの入力を上書きして消します）。
- 切り替えの段取り、バックアップ、セキュリティは [2_運用編.md](2_運用編.md) にまとめています。

| 手元にある機器 | 進め方 |
|---|---|
| 常時稼働できる Windows PC／Windows Server | 1編 → 2編 |
| Synology / QNAP（Intel・AMD、メモリ 4GB 以上） | 3編 → 2編。または Windows PC で動かし、NAS はバックアップ先にする |
| Buffalo・I-O DATA などの NAS だけ | アプリは Windows PC（1編）、NAS はバックアップ先（2編 2-4 の A） |
| まだ何も無い | 数年前の事務用PCやミニPCで足ります（1編 §1 の目安） |

## 作業の流れ（Windows の場合）

1. 開発PCの Node.js を 26 LTS に上げて動作確認する（1編 Step 0。Node.js は 22.12 以上が必須になった）。すぐに上げられない場合は後回しにして、手順 5 のときにサーバー機で回帰テストを実行する（1編 Step 6 の末尾）
2. サーバー機を用意する：IP 固定、スリープ無効、Node.js と Git のインストール（1編 Step 1〜2）
3. フォルダを作って権限を絞り、コードを置く（1編 Step 3〜4）
4. `.env` を作る（週次レポートは、実績の入力を始める日まで `EXPORT_ENABLED=false` にしておく）。DB は空から始める（1編 Step 5）
5. 手動で起動して確認し、**初期パスワード admin123 を変更する**（LAN に開ける前に必ず）→ 止めて回帰テスト → Windows サービスにする → 初期パスワードが残っていないことを確認 → ファイアウォール（1編 Step 6〜8）
6. 別のPCから確認し、再起動しても自動で立ち上がることを確かめる（1編 Step 9）
7. 個人別アカウントの作成（2編 1-2 の 7。パスワードは 13 文字以上・英数字混在でないと登録できない）
8. バックアップのタスク登録と復元テスト（2編 2-3、2-5）。**患者の登録を始める前に済ませる**（登録には数日かかることがあり、その間も毎晩のバックアップが要る）
9. **初期データの登録**（日用品単価の確認、患者、患者ごとの食事単価と上限。2編 1-2a）
10. 実績の入力を始める日に、週次レポートをサーバー側で有効にし、開発PC側を止める（2編 1-2 の 8）
11. 最初の 1 か月は、これまでの Excel での集計も続け、月末に患者ごとの合計額を見比べる（2編 1-3。合わなかったときの扱いも同じ箇所）
12. 月に1回、操作ログ（マスタ管理 → 操作ログ）の「断られた操作・エラー」「ログイン・ログアウト」「サーバーの出来事」を確認する（2編 8章）

## 2026-11-21 にコードへ入れた対応

複数のPCで使う前の点検で見つかった問題を修正し、テストしてあります（詳細は [動作検証.md](../動作検証.md) の S-02）。

- DB の保存を「一時ファイルに書いてから差し替え」にした（保存中の停電・異常終了で DB が壊れない。0バイトの DB を空の DB として上書きしない）
- 実績の保存で DB 全体を書き出す回数を、1日分につき最大16回から1回にした
- 日次入力の「一括保存」が、変更した欄だけを送るようにした（2人が同じ患者・同じ月を開いていても、互いの入力を古い値で上書きしない。ただし朝食・昼食・夕食・サービス提供の状況・加算2つの計6欄は1日分をまとめて送るので、同じ日のこの6欄を2人が別々に直すと、後から保存した人の画面の値になる）。未保存の入力があるときは切り替え前に確認を出す
- `.env` と PDF 用 Chrome の場所を、起動時の作業フォルダやアカウントに関係なく見つかるようにした（Windows サービスで動かすための対応）
- 請求書 PDF の同時生成数を制限した（既定2。メモリ不足の防止）
- バックアップ・稼働確認・初期パスワード確認・保存処理の自己テストのスクリプトを `tools/` に追加した

同じ日の2回目の作業で、残っていた3項目に対応しました（詳細は [動作検証.md](../動作検証.md) の S-03）。

- **依存ライブラリの更新**：`npm audit` の指摘を 16 件から 0 件にした。請求書 PDF に使う Puppeteer を 22 → 25（Chrome 127 → 157）に上げ、PDF の中身が更新前と同じであることを確認した。**Node.js は 22.12 以上が必要**になった（手順書の推奨は従来どおり 26 LTS）
- **パスワードの強度チェック**：13 文字以上・英数字混在などの基準を満たさないパスワードは登録できない（ガイドラインが、二要素認証を使わない場合に求める基準）
- **ログイン失敗時のロック**：同じPCから同じユーザーIDで 5 回続けて失敗すると、そのPCからは 15 分間ログインできない（PCを変えながら続けた場合は、合計 20 回でどのPCからも不可）。管理者が画面から解除できる。管理者がパスワードを忘れたときのために、サーバー機の上で設定し直すツール（`tools/reset-password.js`）を追加した
- **操作ログ**：ログイン、患者の情報の表示・PDF 出力、登録・変更・削除を自動で記録し、管理者が画面で確認・CSV 保存できる。保存先は DB と同じフォルダの `audit`（`C:\hiyou\data\audit`）で、バックアップにも含まれる
- **独立したレビューと修正**：実装後に、セキュリティ・正しさ・運用の3つの観点で別々に点検し、見つかった問題（細工した 1 リクエストでサーバーが停止する、など）を修正した。内容は 動作検証.md の S-03 の表
- **HTTPS 対応**：アプリ側の変更（プロキシの信用設定 `TRUST_PROXY`、待ち受けアドレス `HOST`、Cookie の Secure 属性）を適用した。本物の TLS を終端するプロキシを挟んで動作を確認した（Caddy そのものは未確認）。HTTPS にするかどうかは従来どおり選べる（2編 3章）

2026-11-22 に、上のレビューのあとで書いた修正と文書を、もう一度 3 つの観点で点検しました（詳細は [動作検証.md](../動作検証.md) の S-04）。

- **操作ログの記録漏れを 3 つ修正**：`/` を 1 つ余分に打ったURL（`/api/pdf//…`）で、記録が残らないまま患者の情報や請求書 PDF が返っていた／要求を連打したあとに開いた患者が記録に残らなかった／ID に `%00` を付けると患者ID が記録から抜けた。いずれも、処理せずに断る形に直し、断ったことが記録に残るようにした
- **非常用のパスワード再設定ツール**：画面に案内が出ない、DB の場所が違うと新しい DB を作ってしまう、アプリが動いていても実行できる場合がある、という問題を修正した（2編 8-2 の手順も更新）
- **月次の確認**：操作ログの絞り込みに「サーバーの出来事」を追加した（記録の欠落、サーバー上のツールでのパスワードの再設定、サーバーの起動は、これまでどの絞り込みにも出なかった）。患者ID でも探せるようにした
- **バックアップ**：大きさを変えない書き換えも検出する。DB のバックアップに失敗した晩も、操作ログは 2 本目の置き場へ送る
- テストは、回帰 80 項目・自己テスト 74 項目に増やした

2026-11-23 に、本番に載せる前の確認として、1編 Step 4〜6 と更新手順を GitHub から取り直したフォルダで実際に通し、11-22 の修正と手順書をもう一度点検しました（詳細は [動作検証.md](../動作検証.md) の S-05）。

- **操作ログの画面から記録が消える問題を修正**：URL に行区切りの特殊な文字（U+2028 など）を 1 つ混ぜると、その表示の記録が操作ログの画面・CSV・件数に出なくなっていた（閲覧のみのユーザーでも可能。ファイルには残っていた）。記録として読めない行があるときは、画面に行数を表示するようにした
- **ログのファイル・フォルダが消されたとき**：作り直して記録を続け、「無くなっていた」ことを記録に残す（以前は、フォルダごと無くなると、戻すまで記録されないまま処理されていた）
- **同じ DB を 2 つのプロセスで開けないようにした**：サービスが動いているのに別のポートで手動起動した、アプリが動いている間に再設定ツールを実行した、という場合に、互いの保存を上書きして入力や変更が消えることがあった。2 つ目は「このDBファイルは、ほかのプロセスが使用中です」と表示して中止する
- **手順書**：空の DB から始めるときに登録するもの（単価の確認、患者、食事単価）を追加（2編 1-2a）。準備中のサーバーから週次レポートが送信されないよう、当日まで `EXPORT_ENABLED=false` にする手順に変更。1編 Step 5・6 を「空から始める」場合の表示に合わせ、サーバー機での回帰テストを追加。NAS でリバースプロキシを使うときのポートの設定を追加（2編 3-3）
- **日次入力の画面で、入力が別の患者に保存されることがある問題を修正**：患者の切り替えに失敗したとき（8 時間でのログイン切れ、サーバーの再起動、通信エラー）や、前の患者の応答が遅れて届いたときに、前の患者の表が残ったまま別の患者が選択中になり、その表への入力や食事単価が別の患者に保存されることがあった。表の見出しに患者の氏名を出すようにした
- **金額の食い違いを修正**：無効にした物品に実績があると、月次集計はその金額を含むのに、入力画面と請求書 PDF は含めなかった。無効にした患者（退院など）は、その月に実績があっても月次集計に出なかった。数量・単価に小数を入れられ、金額に端数が出ることがあった（整数だけを受け付けるようにした）
- **食事単価の保存漏れを防止**：食事単価を入れて「一括保存」だけを押すと、単価が保存されなかった（一緒に保存するようにした。保存しないまま切り替えようとすると確認が出る）
- 操作ログのファイルを、同じ名前の別のファイルに置き換えられた・中身を消された場合も、気づいて記録に残す。DB の場所が共有フォルダ（`\\サーバー\共有\…`）のときは起動しない
- **手順の順序を修正**：患者を登録している数日間もバックアップが動くように、バックアップのタスク登録を初期データの登録より前にした。初期パスワードの変更を 1編 Step 6 の独立した手順にし、ファイアウォールを開ける前に確認ツールで確かめるようにした。週次レポートを有効にするのは、実績の入力を始める日にした。Excel との並行期間と、合わなかったときの扱いを 2編 1-3 に書いた
- テストは、回帰 84 項目・自己テスト 82 項目・DB の自己テスト 18 項目に増やし、実際の画面を Chrome で動かして確かめる「画面の回帰テスト」（`tools/ui-test.js`。14 項目）を追加した

## 決めていただくこと

1. **サーバーにする機器**（機種、Windows のエディション、有線LANか、専用機にできるか）。NAS を使うならメーカーと型番
2. **夜間・週末も電源を入れたままにできるか**（月曜 6:00 の週次レポート送信と夜間バックアップの前提）
3. **Wi-Fi で使うPCがあるか、来客や業者の機器が同じネットワークにつながるか**（あるなら最初から HTTPS にする。2編 3章）
4. **バックアップの2本目の置き場**（NAS か USB HDD）と保持期間、月次のオフライン保管の担当
5. **未署名のフリーソフト WinSW をサーバーに入れてよいか**（不可なら Servy かタスク スケジューラ方式。1編 §5）
6. **施設のルールとの関係**：厚生労働省ガイドラインの対象として台帳・規程に載せるか。二要素認証が無い点（パスワードは 13 文字以上で補う）と、本人がパスワードを変更する画面が無い点を、当面は運用で補うことの了承（2編 7章）。操作ログの保存期間と、月次の確認の担当者（2編 8章）
7. **GitHub リポジトリの公開設定**：2026-11-21 時点で公開（誰でも閲覧可）になっています。患者データや API キーは含まれていませんが、意図していなければ非公開に変えてください
8. 担当者が不在のときに、再起動と復元を行う代行者
9. **使い始める月**（月の初めからが分かりやすい）と、患者・単価・食事単価を登録する担当者、最初の月に Excel の集計と見比べる担当者（2編 1-2a、1-3）。最初の月の請求を、Excel とアプリのどちらの数字で行うか
10. **退院・転棟したときの扱い**：退院した患者は「有効」を外す（「削除」は、その患者の実績もすべて消えるので使わない）。転棟は、患者管理で病棟を変える（2編 1-2 の 11）
11. サーバー機の Windows の管理者アカウントを、だれが持つか（操作ログのファイルや DB を直接さわれるのは、この人だけ。2 名までにする）
12. サーバー機のディスクを暗号化する場合（BitLocker。2編 4章）、回復キーの保管場所と担当
13. 停電への備え（無停電電源装置を付けるか。付けない場合は、停電から戻ったあとに自動で電源が入る設定にする。1編 Step 1）
